# 类型化回答可以绕过对话理解代理直接写入规划需求单

`app/chat/executor.py` 开头写着这个模块「有意永不接收或读取用户原始消息」，并确立了一条架构原则：语言模型校验后的结构化决定，是语言理解与业务状态之间唯一的边界。本次改动要为提问卡片上的候选项新增一条写入路径——点击「傍晚」直接把 `arrival_time` 写进需求单，既不经过语言模型，也不产生对话消息。这表面上是在那条原则上开了一个后门。我们决定**允许这条例外，但把它限制在服务端自己定义的封闭选项上**：回答必须对应服务端当前正在询问的那个字段，取值必须来自服务端给出的候选项，字段不匹配一律拒绝。

## Status

accepted

## Considered Options

- **让候选项也走普通对话消息**：否决。候选项已经带着确切的字段和值，再绕一圈语言模型去解析，既慢又可能解析错；多轮问答每点一下都要等几秒，逐项提问的体验会垮掉。
- **开放一个可写任意字段的结构化端点**：否决。那等于把已有的 PATCH 接口重开一遍，前端就获得了「随时写任意字段」的能力，校验面变大，而且与「任何时刻只有一个待问字段」的模型自相矛盾。
- **把自由文本也交给结构化端点解析**：否决。那等于把语言理解层的职责搬进业务层，是真正的越界。

## Consequences

- 这条例外之所以成立，是因为此时**没有需要理解的东西**：选项由服务端定义，用户只是在封闭集合里选一个。架构原则约束的是「理解」，不是「写入」。
- 用户自由输入的回答仍然必须走对话理解。两条路径都写同一条需求单、都触发同一套校验与记忆刷新，因此不会产生两套真相。
- 因为结构化回答不产生对话消息，抵达与返程时刻**在物理上不可能**被会话记忆提炼进长期记忆（见 ADR 0001）。这条例外反而加固了那条决定。
- 代价是不广播事件：另一个已打开的标签页不会自动同步，要重新加载会话才能看到。这是明确接受的局限。
- 将来若要新增字段提问，必须同时在服务端的提问清单与可回答字段校验里登记；只加清单不加校验会让这条例外悄悄扩大。
