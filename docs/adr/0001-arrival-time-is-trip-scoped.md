# 抵达与返程时刻是行程范围内的结构化事实，不进入长期记忆

用户在对话里说「11月7日傍晚抵达」，生成的行程却从当天上午 9 点开始排。根因是系统里根本不存在「抵达时刻」这个概念：规划需求单只有起止日期，规划图状态与路线结构都没有承载抵达时刻的字段，用户原话也不会进入规划提示词。我们决定把抵达与返程时刻做成规划需求单的一等结构化字段（与起止日期平级），随提交快照冻结后贯穿规划链路，并且**永不写入长期记忆**。

## Status

accepted

## Considered Options

- **写进 `trip_constraints` 的 `schedule_preference` 自由文本**：否决。它会被 `compatibility_preferences()` 揉进 `habit_preference` 字符串，没有任何规划节点负责执行它，等于把问题从"没有字段"挪到"字段没人读"。
- **升级为用户画像中可长期记住的作息偏好**：否决。抵达时刻是**行程**属性而不是**人**属性；写进画像会在下一次出行中被误用，而现有记忆抽取已经把任何含日期的内容判为一次性并主动拒绝，放开这个口子等于推翻那条设计。

## Consequences

- 抵达与返程时刻必须随提交快照冻结，因此修改行程会继承它，不需要额外接线。
- 由于它不在长期记忆里，**每一趟行程都必须重新收集**。收集只能是软追问：按既有规格，抵达时刻是可选信息，问不出也不得阻止需求单进入可提交状态。
- 用户坚持模糊表述（如「就傍晚吧」）时不得静默丢弃：必须保留原话，并配合一个保守下界用于提示词约束与时间核验阈值，否则时间核验无阈值可算。
