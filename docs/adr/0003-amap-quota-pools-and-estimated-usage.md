# ADR 0003：高德配额按服务组分池预留，并且把"估算"写进语义

- 状态：已接受
- 日期：2026-09-16
- 相关规格：`openspec/specs/amap-quota-guard`、`openspec/specs/amap-rest-call-channel`

## 背景

后端使用一把高德 Web 服务 Key，落在四个 REST 接口上：`place/text`、`place/around`、`weather/weatherInfo`、`direction/walking`。高德自 2025-05-20 起取消日配额，改为按「服务组」共享的**月配额**：

| 服务组 | 本项目用途 | 月配额（已认证个人开发者） |
| --- | --- | --- |
| 基础搜索服务 | 关键字搜索 + 周边搜索 | 5,000 |
| 其它基础服务-天气预报 | 天气查询 | 5,000 |
| 基础LBS服务 | 步行路径规划 | 150,000 |

三个约束塑造了这次设计：

1. **额度按服务组共享，不按接口。** 同组内所有接口、同一账号下所有 Key（含 JS API Key）合计消耗同一份额度。
2. **官方没有配额查询 API。** 已逐一核对全部 Web 服务文档、CLI 文档与 MCP Server 文档，确认不存在；官方唯一指引是登录控制台查看。
3. **月配额超限的返回码未被文档化。** 官方错误码表只有日调用量版本（`10003` / `10044`），而日配额已取消。

搜索池最紧：一次 5 天单城市规划消耗 13 次搜索（3 次景点 + 10 次餐饮周边），占月额度的 0.26%。

## 决策

### 一、按服务组分池，而不是一个总额度

三个池的额度差 30 倍，失败后果也完全不同：搜索池耗尽使规划直接不可用；天气池耗尽只是降级为"按晴天规划"（该降级路径已存在）；LBS 池耗尽只影响步行路线绘制。

若合并为一个计数器，必然出现"天气额度用完导致规划被拦"这类结果——用户无法理解，且与真实约束无关。

### 二、在请求发出前预占，而不是事后记账

事后记账无法阻止超额：额度用尽后的请求已经发出去了。预占让"额度不足"表现为**一次都不发**。

### 三、计数口径是实际 HTTP 请求，不是逻辑调用

现有代码有高德层（最多 4 次）× HTTP 层（最多 3 次）两层重试，一次逻辑调用最坏展开成 12 个真实请求。高德按收到的请求扣配额，因此只有按请求计数才不失真。

代价是偏保守：网络超时、请求可能根本没到达高德，我们仍然扣了。偏保守正是本特性的目的。

### 四、计数落在 SQLite，且不做内存缓冲

考虑过 Redis 与内存缓冲，都否决了：

- **Redis 不行**：它是可选依赖，未配置 `REDIS_URL` 时整个缓存层静默失效（`app/core/cache.py:24-27`）。配额保护绝不能因为"没配 Redis"而恰好失效——那正是最需要它的环境。
- **内存缓冲 + 定时刷盘不行**：崩溃丢写会**低估**用量。这个特性的全部价值在于不低估，因此允许的失效方向只有"高估"。每请求一次同步 SQLite 写入（毫秒级，一次规划约 13 次）代价可接受。

### 五、把"估算"写进领域语义，而不是留给文档

本地计数从部署时刻起从 0 开始，而用户在控制台看到的当月已用量可能已有几百次。官方没有查询接口，所以这个缺口**无法自动关闭**，只能人工录入补正。

这带来一个容易做错的推论：如果对外把它说成"剩余额度"，用户会以为程序知道真实余量，进而信任一个可能高估的数字。因此领域语言里把它定为**已用量（估算）**，并提供"用量对账"这个独立动作，而不是把它包装成权威余额。

对账本身也不是两个数字的简单合并。"控制台读数"与"本地计数"不在同一时间点上：前者是**对账那一刻**的快照、已含此前的本地调用，后者是**累计量**。所以正确的式子是「控制台读数 + 对账之后新发生的本地调用数」，为此表里存一个 `counter_at_reconcile` 作为锚点。相加会重复计数，取 max 会漏掉对账之后的增量——这两种写法都试过，都被测试推翻了。

### 六、异常类型统一，使上层不需要知道失败来自本地还是远端

本地预占失败不产生 HTTP 响应，但抛出的异常类型与 `public_code` 与高德返回配额错误时完全一致。这样 `app/runtime/scheduler.py:178-185` 已有的 `getattr(exc, "public_code", ...)` 读取路径直接可用——它本来就是为此设计的，只是裸 `RuntimeError` 一直没有这两个属性。

### 七、默认即开启拦截

默认限额取官方数值的 95%（4,750 / 4,750 / 0-即不限）。5% 边际覆盖"被拒绝的请求是否计入配额消耗"这个官方未说明的口径。

默认值非 0 意味着本次变更上线后默认就拦截。这是刻意的：审计发现程序在额度见底时的实际行为是**加倍索取**（12 倍重试放大），默认不设防明显更坏。

## 后果

### 好处

- 额度不足时连一次请求都不发，超额在结构上不可能发生。
- 天气池与搜索池的隔离使"天气额度用完"不再能弄挂规划。
- 故障原因对用户可见，且区分"等重置"与"需提工单"两类完全不同的处置。
- 并发约束的生效点从两处收敛为一处，三条同步路由首次获得约束。

### 代价

- 每请求一次同步 SQLite 写。相对 10–60 秒的规划时长可忽略，但在高并发下会串行化写。
- 计数偏保守：超时请求也被扣。这会让本地估算**低于**控制台的真实余量（高估消耗），朝向安全的一侧。
- 只能保护后端发出的请求。前端 JS API Key 与移动端 Key 在服务端不可见。

### 已知缺口

1. **前端 JS API Key 不在保护范围内。** `AMap.Map` / `AMap.Driving` 由浏览器直接消费。当前前端没有使用任何 JS 侧 POI 搜索插件（已核对：只用 `Map` / `Driving` / `Walking` / `Polyline` / `Marker` / `InfoWindow`），因此不蚕食紧张的 5,000 搜索池；但将来若引入 JS 搜索插件，会静默蚕食。堵住它需要把 JS 侧调用也代理到后端。
2. **月配额重置时刻是推断。** 官方未公布按自然月、滚动 30 天还是按认证日对齐，也未公布时刻与时区。本实现按 `Asia/Shanghai` 自然月推断。
3. **月配额超限的返回码未知。** 需对真实 Key 实测确认，已列为交付后的待办。
4. **多份独立数据库的横向扩展会各自计数**，合计用量超过单实例视角。本项目的部署形态（单容器 + 单 SQLite 文件）不受影响。

### 一个需要用户核对的时效风险

定价页工具提示原文："非商业目的使用的个人认证开发者……享有的1年的免费月配额量（自注册认证之日起计算）。"语义有歧义，但若字面成立，认证满一年后免费额度可能归零——届时本特性会立刻从"保护"变成"常态拦截"。已列为用户待办：登录控制台核对到期日。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 超限时优雅降级，返回空结果继续规划 | 会产出违反"景点必须来自高德搜索结果"硬性约束的行程，Reviewer 会打回，最终仍是失败任务，只是更晚更贵 |
| 事后记账 + 超限报警 | 报的是已经发生的超额，阻止不了它 |
| 统一一个总计数器 | 三个池额度差 30 倍、失败后果不同，会产生用户无法理解的拦截 |
| 计数挂到 Redis 缓存层 | Redis 未配置时静默失效，配额保护会恰好失效 |
| 内存缓冲 + 定期刷盘 | 崩溃丢写导致低估，失效方向错误 |
| 合并午晚餐搜索以省额度 | 会改变候选池构成，属于影响规划质量的改动，与本变更目标不同源 |
| 城市级长 TTL 景点缓存 | 引入 POI 陈旧化（评分、营业时间、关店），收益与风险都不在本变更范围内 |
