## 三个池的模型

### 为什么要分池

三个池的额度差 30 倍，失败后果也完全不同：

- **`search` 耗尽** → 规划直接不可用。景点池拿不到就无法满足"景点必须来自高德"的硬约束；餐饮拿不到则每天无候选餐厅。
- **`weather` 耗尽** → 降级为"按晴天规划"，行程照常产出。已有降级路径（`app/planning/helpers.py:649-654`）。
- **`lbs` 耗尽** → 步行路线画不出来，行程其余部分照常。

合成一个计数器必然出现"天气额度用完导致规划被拦"这类荒唐结果。

### 池定义

每个池 = 官方服务组。池内的限额、已用量、预警状态彼此隔离，且**不跨池抵消**。

`bucket` 的取值即 `search` / `weather` / `lbs`，与官方服务组一一对应；代码里用枚举而非裸字符串。

### 预留与消耗的语义

一次"逻辑调用"与一次"HTTP 请求"不是一回事，这是本设计最核心的一处区分：

**预留单位 = HTTP 请求，不是逻辑调用。** 理由：高德按实际收到的请求扣配额，而现有代码有高德层（`poi.py:26` 等，最多 4 次）× HTTP 层（`http.py:57`，最多 3 次）两层重试。若按逻辑调用计数，一次失败搜索会在盘面上记为 1、实际消耗 12，本地计数立刻失真。

因此：**每个 HTTP 请求发出前各占 1 次额度。** 代价是偏保守（网络超时、请求可能根本没到达高德，我们仍然扣了）。偏保守正是本特性的目的。

### 缓存的层间关系

缓存层与配额层**互不依赖**，这一点必须保持：

- 命中缓存 → 不发生 HTTP 请求 → 不占额。缓存层不需要知道配额层的存在。
- 未配置 `REDIS_URL` → 缓存静默失效 → 每次都真实调用 → 每次都占额。配额保护仍然有效，因为它在缓存之外。

绝不能让配额计数依赖 Redis：那正好把"保护"变成"没有保护"。

### 提前占额而非事后记账

占额发生在**请求发出之前**。顺序是：

1. 判断是否命中缓存；命中则直接返回，不问配额。
2. 未命中 → 预占 1 次额度。
3. 若预占失败（额度不足）→ 抛出配额异常，**不发出网络请求**。
4. 预占成功 → 发请求。

第 3 步是关键：额度不足时连一次请求都不发，这是硬拦截与"事后记账"的全部差别。

### 原子性

检查与自增必须原子，否则并发请求会各自通过检查后一起超支。实现约束：

- 写操作用显式 `BEGIN IMMEDIATE` 事务（仓库既有风格，`app/runtime/repositories.py:157` 等多处）。
- **预留是同步写，不走 `asyncio.to_thread` 之外的异步缓冲。** 崩溃丢写会低估用量，是安全方向上不可接受的错误方向。
- 单次预留是一次短 SQLite 写（毫秒级）。一次 5 天规划约 13 次预留，累计开销相对于 10–60 秒的规划时长可忽略。

选择"同步写、无内存缓冲"而不是"内存缓冲 + 定期刷盘"，是因为后者的失效模式是**静默低估**，而本特性的全部价值在于不低估。

### 表结构

新增一张表，按（池，月份）唯一：

```
amap_quota_usage(
    bucket                TEXT    NOT NULL,   -- search | weather | lbs
    month                 TEXT    NOT NULL,   -- YYYY-MM，Asia/Shanghai
    counter_calls         INTEGER NOT NULL DEFAULT 0,  -- 本服务累计发出的请求数
    counter_baseline      INTEGER NOT NULL DEFAULT 0,  -- 对账时录入的控制台读数
    counter_at_reconcile  INTEGER NOT NULL DEFAULT 0,  -- 录入那一刻的 counter_calls
    warning_sent_at       TEXT,               -- 该池该月是否已发过阈值预警
    updated_at            TEXT    NOT NULL,
    PRIMARY KEY (bucket, month)
)
```

**为什么绝对值拆成三列，而不是直接存一个 `used`：**

用户侧的录入语义是"设置本月已用**绝对值**"（从控制台读到的数字）。若直接覆写单一 `used` 列，会**丢掉本地自动计数**——用户在月中对账一次，此后本地计数就从那个数字继续，两者会互相覆盖。

拆成两列后：对外 `used = counter_calls + counter_offset`；录入绝对值时，把差值写入 `counter_offset` 并记下基准，`counter_calls` 不受影响，本地计数继续独立累加。

### 月份边界

`month` 由 `Asia/Shanghai` 时区的当前时间计算（`YYYY-MM`）。跨月时新月份没有行，自然从 0 开始，无需重置任务。旧行按需清理（保留 13 个月）。

**这是一处推断。** 官方未公布月配额的重置时刻与是否自然月。文档与代码注释必须写明"按自然月推断"，不能写成已确认事实。

### 对账的合并语义（实现中被测试推翻过一次，这里记下正确式子）

直觉上「已用量」像是两个数的合并，但**既不能相加、也不能取 max**。原因是这两个数不在同一时间点上：

- `counter_baseline` —— 用户对账那一刻从控制台读到的账号月内已用量。它覆盖**截至那一刻**的全部消耗（含本服务此前的调用），但对之后的本地调用一无所知。
- `counter_calls - counter_at_reconcile` —— **对账之后**新发生的本地调用数。

正确式子是：

```
used = counter_baseline + (counter_calls - counter_at_reconcile)
```

- 相加会把对账**之前**的本地调用重复计一次；
- 取 max 会**漏掉**对账**之后**的本地增量——它隐含假设控制台数字包含此刻的本地计数，而控制台读数是一个时间点上的快照，不可能包含对账之后才发生的调用。

`counter_calls` 全程只增不改，是纯累计量；对账只写 `counter_baseline` 与 `counter_at_reconcile`。这个式子在「从未对账」（两者均为 0）时退化成纯本地计数。

**这是一处刻意的模型修正。** 最初的设计用单个 `counter_offset` 表达"人工补正量"并令 `used = counter_calls + counter_offset`，被测试直接推翻：那个式子在一般情形下会重复计数或吃掉本地计数，只有"对账后立刻再对账一次"才自洽。规格里对应的 requirement 与 scenario 一并重写为时间锚定语义。

## 「高德 REST 调用通道」

新增 `app/providers/amap/channel.py`，作为**唯一**允许发出高德 REST 请求的入口。

### 现状

8 处真实请求点，散在 4 个模块：

| 出口 | 位置 | 当前是否受并发约束 |
| --- | --- | --- |
| `_text_search_raw`（同步） | `poi.py:24-35` | 否 |
| `_text_search_raw_async` | `poi.py:38-48` | 是（经 `http.py:100`） |
| `search_around_pois`（同步） | `poi.py:53-90` | 否 |
| `search_around_pois_async` | `poi.py:93-126` | 是 |
| `search_attraction_pois`（同步，死代码） | `poi.py:131-162` | 否 |
| `search_attraction_pois_async` | `poi.py:165-193` | 是 |
| `fetch_forecast` / `_async` | `weather/amap.py:24-85` / `:88-127` | 否 / 是 |
| 内联 `httpx.get` | `plan_routes.py:595-605` | **否，且绕过 `http_get_json`** |

### 改法

1. `direction/walking` 的 URL 收进 `client.py` 常量（现为 `plan_routes.py:595` 的内联字面量）。
2. 通道提供单一 async 函数，参数为 URL、查询参数、池归属；返回已解析的 JSON。
3. 通道内部顺序固定为：失败分类 → 预占额度 → `provider_slot("amap")` → HTTP 请求 → 退出码/业务码判定 → 必要时退避重试（每次重试同样预占）。
4. 三条同步路由（`/api/poi/search`、`/api/poi/nearby`、`/api/route/walking`）由 `def` 改为 `async def`，改走通道。它们本来就是 I/O 等待，改成 async 不损失任何东西，并顺带获得并发约束——目前这三条**完全绕过**并发信号量。
5. `poi.py` / `weather/amap.py` 不再直接调 `http_get_json(_async)`，改为调通道。
6. 删除同步版 Amap 客户端函数。

**顺序不能颠倒。** 预占必须在 `provider_slot` 之后也要保持"先占额再发请求"——即占额要早于任何网络动作，否则排队等信号量期间额度可能已被别的请求用光。

### 统一到 async 的收益

现在同步/异步各写一遍 limiter 与重试逻辑，且只有异步路径受 `provider_slot` 约束。合并后：

- 限流点从两处变一处；
- 三条同步路由首次获得并发约束；
- 重试放大逻辑只有一份实现，计数口径不可能分叉。

### 缓存键的串味风险

现有 `poi_cache_key(city, keyword)`（`app/core/cache.py:80-82`）**不含 `types` / `offset` / `radius`**。直接复用会串味：景点搜索与餐饮搜索在同一个关键词下都是 `tripagent:poi:{city}:{kw}`，一个返回风景名胜、一个返回餐厅，互相污染。

周边搜索与步行路线必须建**新命名空间**的新键，且键必须包含所有影响结果的参数（周边搜索含坐标/半径/类型/offset；步行路线含起终点坐标对）。

不修改既有键的构成：那会改变 `/api/poi/search` 的手动编辑缓存行为，属于本变更范围外的语义变化。

## 错误分类

高德 v3 响应为 `{"status", "info", "infocode", ...}`。现有代码**只读 `info` 字符串**（`poi.py:31` / `:44` / `:86` / `:122`），完全不读 `infocode`。有的 `infocode` 没有对应的 info 名，反过来也一样，所以两者都要读。

### 三类语义

| 类别 | 语义 | 处理 |
| --- | --- | --- |
| `quota` | 配额/权限类——继续请求没有意义，且消耗已无价值 | **立即失败，不重试**，携带 `amap_quota_exhausted` |
| `throttle` | 限流类——降速后可以恢复 | **退避重试**（保留现有行为） |
| `other` | 其他业务错误 | 不重试，沿用现有报错语义 |

### 归属

`quota`（含现有集合成员与需新增者）：

- `DAILY_QUERY_OVER_LIMIT`
- `USER_DAILY_QUERY_OVER_LIMIT`
- `USER_ABROAD_DAILY_QUERY_OVER_LIMIT`
- `ABROAD_DAILY_QUERY_OVER_LIMIT`
- `USER_KEY_RECYCLED`
- `INVALID_USER_KEY` / `SERVICE_NOT_AVAILABLE`（权限与未开通类）

> **注意**：日配额已于 2025-05-20 取消，`DAILY_QUERY_OVER_LIMIT` / `USER_DAILY_QUERY_OVER_LIMIT` 现在可能不再触发。但官方错误码表**未给月配额条目**，所以这两个历史码仍必须归入 `quota` —— 如果高德把月配额超限复用成这两个码之一，我们能正确拦截；如果返回未文档化的新码，见下面的兜底。

`throttle`：

- `CUQPS_HAS_EXCEEDED_THE_LIMIT`
- `CKQPS_HAS_EXCEEDED_THE_LIMIT`
- `CQPS_HAS_EXCEEDED_THE_LIMIT`
- `QPS_HAS_EXCEEDED_THE_LIMIT`
- `ACCESS_TOO_FREQUENT`
- `GATEWAY_TIMEOUT`

`other` 中的特例——**失败但不应建议重试**：

- `IP_QUERY_OVER_LIMIT`：官方排查策略是"封停后无法自动恢复，需要提交工单"。文案必须与"额度用完"区分开，否则用户会白等到下个月。

### 兜底规则

未识别的 `status != "0"` 响应、网络异常、JSON 解析失败：**保留现有语义**（按逻辑调用判定，不改变现有失败行为）。

这条兜底故意保守：本变更不应让未知错误的表现变差。

### 本地闸门也走同一异常类型

本地预占失败不产生 HTTP 响应，但异常类型与 `public_code` 与高德返回配额错误时**完全一致**（`amap_quota_exhausted`）。这样 `app/runtime/scheduler.py:168-189` 已有的属性读取路径不需要知道失败来自本地还是远端。

## 用户可见的失败原因

`app/runtime/scheduler.py:178-185` 已经在读 `getattr(exc, "public_code", ...)` 与 `getattr(exc, "public_message", ...)`，只是裸 `RuntimeError` 没有这两个属性，所以落到默认文案。异常类带上这两个属性即可打通，无需改调度器。

| `public_code` | 文案 |
| --- | --- |
| `amap_quota_exhausted` | 今日额度已用完…（按池给出具体服务名与重置时刻） |
| `amap_access_denied` | 高德密钥不可用或已失效，请检查 `AMAP_API_KEY` 配置 |
| `amap_ip_restricted` | 当前 IP 触发了高德访问限制，需要在高德控制台提工单解封，请勿等待自动恢复 |

文案里的"重置时刻"必须来自同一处月份边界计算，不能各处硬编码字符串。

## 只在文档里说明、不做特殊处理的缺口

**本地计数器不知道"部署前已经用了多少"。** 本地计数从部署时刻起从 0 开始，而用户在控制台看到的当月已用量可能已有几百次。如果不补正，硬拦截会在真实额度用尽之后**再放行几百次**。

补法是人工录入绝对值（见上文表结构与端点设计）。但必须清楚：这是**人工对账**，不是自动同步。文档与 UI 文案都要写明这一点，不能让用户以为程序知道真实剩余量。

**5% 安全边际的来源。** 官方未说明"被拒绝的请求是否计入配额消耗"。若计入，则本地计数会低估（我们没数被拒的那次）；若不计入，则本地计数准确。取 5% 边际覆盖前者。这是**估算参数，不是对账结果**。

## 预警

达到池限额的 80% 时，该池该月**只发一次**预警。`warning_sent_at` 字段记录已发状态，避免重复打扰。

预警的呈现：作为 Run 事件进入对话时间线。这需要把事件类型加进 `app/runtime/models.py` 的 `PlanningBriefEvent`。该模型是图来源自定义事件的**唯一白名单**（`extra="forbid"`），不加就发不出去。

同时提供只读端点暴露三个池的 `limit / used / remaining / warning_threshold / warning_sent`。

## 配置

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `AMAP_QUOTA_SEARCH_LIMIT` | `4750` | 基础搜索服务月配额。官方原值 5,000。 |
| `AMAP_QUOTA_WEATHER_LIMIT` | `4750` | 天气预报月配额。官方原值 5,000。 |
| `AMAP_QUOTA_LBS_LIMIT` | `0` | 基础LBS服务月配额。**0 = 不限制**。官方原值 150,000。 |
| `AMAP_QUOTA_WARNING_RATIO` | `0.8` | 预警阈值比例，三个池共用。 |

`.env.example` 必须为每个变量写出官方原值与来源链接，让用户一眼看出数字怎么来的、随时能改回去。

**校验：** 限额必须是 `>= 0` 的整数，否则启动失败（而不是静默当作不限）。把 0 定义为"不限制"是刻意的：LBS 池默认必须是这个语义，且用户可能想临时关掉保护。

## 迁移与兼容

1. **新增表**：`init_db` 里加 `CREATE TABLE IF NOT EXISTS`，符合仓库既有模式（`app/core/database.py:31-234`）。无 schema 版本号机制，本变更也不引入。
2. **删除同步函数**：`tests/test_manual_edit_api.py` 直接 import 并调用了 `poi_mod.search_city_pois`，需改为 async 版本。
3. **行为变更**：删除 `RuntimeScheduler.amap_capacity` 时，保留 `amap_limit` 构造参数但标记为不再使用，避免 `container.py:37` 与既有测试构造点全线报错。`RUNTIME_AMAP_CONCURRENCY` 环境变量保持有效（真正生效的位置在 `app/core/async_resources.py:13`），只是注释里要写明生效点。
4. **默认值即生效**：默认限额非 0，所以本次变更上线后**默认就开启拦截**。这是刻意选择（问题二的存在使得默认不设防明显更坏），但需要在变更说明里明确告知。
5. **`/api/poi/search` 缓存行为不变**：不修改既有缓存键构成。

## 风险

| 风险 | 影响 | 处置 |
| --- | --- | --- |
| 月配额超限返回未文档化的新 `infocode` | 无法识别为配额类，会按未知错误冒泡 | 写成实测待办；兜底下失败语义不变，不会静默重试放大 |
| 自然月重置假设错误（实际是滚动 30 天） | 月初可能低估真实余量 | 文档标注为推断；已用量可人工补正 |
| 账号「1 年免费月配额」到期 | 免费额度归零，拦截变成常态 | 列为用户待办：核对控制台到期日 |
| 前端 JS Key 将来引入 POI 搜索插件 | 静默蚕食 5,000 搜索池 | 列为已知缺口写入文档 |
| 默认即开启拦截，误配置导致规划不可用 | 用户体感为"坏了" | 限额校验启动即失败；错误文案指明是哪个池、何时重置、以及如何调整配置 |
| `IP_QUERY_OVER_LIMIT` 被误当成"等重置" | 用户白等，实际需提工单 | 单独的错误码与文案 |
| 多进程部署时各自独立计数 | 合计用量超过单进程视角 | 计数落在共享的 SQLite 文件，事务保证跨进程原子；文档注明不支持多份独立数据库的横向扩展 |

## 测试策略

- **单元**：池定义、限额解析与校验、月份边界（含跨月、时区不随容器变）、绝对值录入的差值语义、错误分类三类归属、阈值预警只发一次。
