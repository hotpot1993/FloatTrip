## Context

旅行对话页已经具备持久化消息、PlanningBrief、独立 Run 生命周期、统一活动时间线和可编辑的确认摘要。问题不在缺能力，而在**交互顺序**与**谁来提问**：

- `DialogueActionExecutor._apply_brief`（`app/chat/executor.py:84-140`）在拿到任意非空 `brief_patch` 时立刻 `upsert_active` 并广播 `planning_brief.updated`，前端 `ChatState.activityItems`（`frontend/chat-state.js:274-284`）随即把 TRIP NOTE 卡片插进时间线——目的地和日期还是空的就开始展示。
- 「下一个该问什么」没有任何代码负责。后端只算必填全集（`app/core/planning_brief.py:21-35`），追问文本由语言模型临时决定；`DialogueClarification.field` 与 `.options` 无消费方，`executor.py:31` 只取 `.question` 当一句纯文本。
- 前端 `StructuredInteractionInput`（`frontend/pages.jsx:992-1051`）已经实现了日期范围、单选、多选与文本降级四类控件，但唯一调用点是 Run 的 `waiting_user`（`pages.jsx:1160-1170`），与 PlanningBrief 无关。
- `ChatState.activityItems` 是「一个实体 → 一个时间线项」的投影，无法表达同一条 brief 派生的多轮提问。
- 用户在从未提到抵达时刻时不会被询问，第一天仍从 09:00 起排——`respect-trip-time-window` 明确搁置的这一半。

本次改动同时推翻了上一轮的一个决定：`respect-trip-time-window` 定的是「用户没主动提到抵达/返程就绝不追问」，理由是避免像查户口。逐项提问流程正是让主动询问变得可接受的那个机制，因此该决定被本次取代。

**约束**：`status == 'ready'` 被 `PlanningBriefRepository.submit()`（`app/runtime/repositories.py:543-598`）、`_confirm_plan`（`app/chat/executor.py:142-190`）与 `POST /api/runs`（`app/api/runtime_routes.py:399-401`）三处硬依赖；`planning_briefs` 上存在部分唯一索引 `idx_one_active_brief_per_conversation`（`app/core/database.py:215-219`），一个会话最多一条 active brief；`data/app.db` 目前零业务数据。

## Goals / Non-Goals

**Goals:**

- 让用户在需求被整理成摘要之前，先通过逐项提问把要求说清楚。
- 把「问什么、问几个、什么时候问完」变成服务端可计算的确定行为，而不是模型每次的心情。
- 让候选项点击成为一次快速、准确、可离线测试的写入，而不是绕一圈语言模型。
- 在零表结构变更、零数据迁移的前提下，让刷新前后的提问状态完全一致。
- 让抵达/返程时刻被主动询问，从而补上第一天起点这个已知缺口。

**Non-Goals:**

- 不改变 `status`、`ready`、`required_brief_fields` 与 `submit()` 的语义。
- 不改变 Run 生命周期、事件白名单的既有形状、并发调度与 provider 配置。
- 不做数据迁移，也不回填既有 brief 或快照。
- 不引入多渠道广播（会话级 SSE topic）或前端 DOM 测试设施。
- 不修改 `mobile-app/` 与 `mobile-prototype/`。
- 不补齐已归档 change 中另外三项未实现行为（另见 `complete-conversation-interaction-gaps`）。

## Decisions

### 1. 提问由服务端确定性驱动，语言模型不再决定问什么

服务端维护一张固定的六项提问清单，依据 PlanningBrief 当前内容与已跳过字段算出**唯一的下一个待问字段**，并下发结构化问题：字段名、问法、候选项、剩余项数、当前输入类型。语言模型只负责理解用户的自由输入并写字段。

备选是继续让语言模型自行追问（现状的 `clarification`）。被否决：无法保证问完、可能重复问或跑题，「是否问完」取决于模型当轮输出，自动化测试只能写成概率性断言；而 `missing_fields` 只认必填，模型没有任何收敛压力。

### 2. 判定规划意图就创建 brief，哪怕一个字段都没提取到

现状是 `_apply_brief` 在 `brief_patch` 为空时返回「我还需要一点旅行信息，才能继续整理这趟行程。」并且不创建 brief（`executor.py:88-89`）。改动后，只要意图是 `create_plan` 或 `update_brief`，即使本轮没有提取到任何字段也创建（或复用）brief 并进入提问，第一项是目的地。

理由：用户说「我想出去玩」正是最需要被逐项问清楚的场景，而现状下这个场景永远进不了提问流程。代价是语言模型把闲聊误判为规划意图时会凭空开出一张空需求单；缓解手段是提示词把「规划意图」限定在显式表达（含目的地、日期、天数任一，或明确要求规划），并接受一次可被「清除这份需求」撤销的误开。

### 3. 提问清单固定为六项并严格串行

顺序：目的地 → 起止日期 → 抵达时刻 → 返程时刻 → 本次预算 → 旅行偏好。

- 硬信息优先：抵达与返程直接决定第一天和最后一天能不能排，越早拿到越好；天数由日期自动算出（`_normalize_days`，`executor.py:344-348`），不占一轮。
- 必答排在前面，因此「必填不齐时必须继续问」与「可选字段至多问一次」不会冲突。
- 严格串行：任何时刻时间线上最多一张待答卡片。

备选是「一张卡片装多个待填字段」或「偏好合并成一张多选卡」。被否决：前者让「一问一折叠」的记录模型失效，且部分填写的提交语义很难定义；后者会让折叠行变成一行多值，收益不抵复杂度。

### 4. 日期是一道题，用日期范围控件

候选项形态为出发日 + 返回日，复用现有 `date-range` 控件（`pages.jsx:1024-1029`）。只知道天数的人走自由输入，由语言模型折算为返回日期（`prompts.py` 规则 2 已具备该行为）。

备选是「出发日 + 天数」。被否决：「玩 5 天」是否包含往返当天存在真实歧义（后端按 `(end - start).days + 1` 计算），而日期范围没有歧义；且需要新写一个日期加数字的控件。

因此「日期」在提问清单里是一个字段组而非单一字段，服务端下发的 `field` 为 `date_range`，回答时一次性写入 `start_date` 与 `end_date`。这是「只能回答当前待问字段」校验的必要放宽，见决策 7。

### 5. 候选项点击走结构化回答接口，自由输入走对话通道

新增端点（形如 `POST /api/planning-briefs/{brief_id}/answers`，请求体 `{field, value}`），直接写入 brief 并返回更新后的 brief 与下一个提问。

- 快：点击一次立即推进，不需要等一轮语言模型（几秒）。
- 准：候选项已经带着确切的字段和值，再让模型解析一遍既不必要也容易出错。
- **天然满足 ADR-0001**：因为它不产生对话消息，抵达时刻就不可能被会话记忆提炼进长期记忆。这是该架构的直接好处，而不是巧合。
- 自由输入无法被字段化，仍走 `POST /api/conversations/{id}/messages`，由语言模型理解后写字段。

### 6. 结构化回答接口只能回答服务端当前正在询问的字段

请求必须携带 `field`，服务端校验它等于当前待问字段（或该字段组），不等则返回 409 且不修改 brief。

理由：`executor.py` 开头的架构原则是「语言模型校验后的结构化决定是语言理解与业务状态之间唯一的边界」。这个新接口确实绕过了模型，但只在**服务端自己定义的封闭选项**上绕过——没有需要理解的东西。把范围收窄到「当前这一题」，前端就无法获得「随时写任意字段」的能力，同时顺带解决了双击与双标签页并发点击的竞态。

这条例外单独由 ADR 记录（见 `docs/adr/0002-typed-answers-bypass-the-dialogue-agent.md`）。

### 7. 「已问过/已跳过」全部由 brief 派生，跳过写入 `data.declined_fields`

不新增表、不新增列。跳过记录作为显式列表写进 `brief["data"]["declined_fields"]`（例如 `["arrival_time"]`），「下一个待问字段」= 清单中第一个既无值又未出现在该列表中的字段。

备选一：用「键存在即已处理」的隐式约定，跳过的字段写空值。被否决：把「没问过」和「问过但没要求」压进同一个空值里，后续改动很容易踩坏，而本仓库已经为跨层隐式约定付过代价（`docs.md` 问题十四）。

备选二：新增持久化的提问记录（给消息表加结构化列，或新表）。被否决：`loadConversation` 只回放**活动 Run** 的事件历史（`pages.jsx:239-241`），已结束的 Chat Run 事件不会重放，所以「把提问当成 SSE 事件发出去」在刷新后必然丢失；要真正还原逐条提问的历史顺序就必须改表加迁移，而收益只是折叠行的先后顺序更忠实。

**派生方案的已知代价**：刷新后折叠记录行按固定字段清单排序，而不是用户真实的提问先后。这不影响正确性，只是观感差异。

**必须同步的白名单**：`declined_fields` 会经过 `app/chat/executor.py:132-138` 的 `durable_fields`。若不同步，用户跳过抵达时刻之后再自由输入一句预算，`_apply_brief` 合并后按该白名单过滤就会丢掉 `declined_fields`，抵达时刻会被重新问一遍。

### 8. 提问卡片是活动时间线条目，答完就地折叠

时间线在提问期间由同一条 brief 派生多个条目：已处理的字段折叠成一行「已记录」，当前待答字段渲染成一张提问卡片。全部处理完之后，时间线末尾追加 TRIP NOTE。

这需要改变 `ChatState.activityItems` 现有的「一个实体 → 一个时间线项」模型：由 brief 派生的条目使用 `question:{field}` 与 `record:{field}` 这类稳定 key，保证同一字段在事件重放时不重复出现。

备选是把待答提问固定在输入框上方的「当前待答」区域。被否决：历史问答不留痕，且刷新恢复需要服务端额外重算，与决策 7 的派生方案重复。

### 9. TRIP NOTE 由「收集已完成」触发，并且永不收回

「收集已完成」= 六项全部已答或已跳过。它是一个**只影响展示的派生量**，由服务端计算并随 brief 一起下发；`status`、`ready`、`required_brief_fields`、`submit()` 的语义一字不改。

- `ready` 表示必填信息完整、可以被提交；「收集已完成」表示提问结束了。两者是独立的事实，`ready ⇒ 收集已完成` 不成立。
- 摘要一旦出现就留在时间线并就地更新。若后续操作使日期变为缺失，摘要保持可见并在缺字段处标注待补充，同时在末尾追加对应提问。

备选是直接改 `ready` 的判定。被否决：`submit()`、`_confirm_plan`、`POST /api/runs` 三处硬依赖 `status == 'ready'`，改动会连带破坏提交链路并要求同步修改既有测试，回归面与收益不成比例。

### 10. 用户要求「直接开始规划」＝ 结束提问，而不是跳过确认

用户明确要求开始时，服务端把剩余未处理的可选字段一次性标记为已处理、展示需求摘要，并且**不创建 Run**；只有用户对摘要执行确认动作才创建 PlanningRun。

这移除了主规格 `Explicit formal-planning confirmation` 中「unless the user has issued an explicit supported direct-start command」的例外，因此是 BREAKING 的行为变更。

理由：用户抱怨的是「问题太多」，不是「不想看一眼摘要」；而摘要确认本来就是本产品的核心承诺（把模糊念头变成可出发的行程，中间要有人点一次头）。移除例外还顺带消除了一个真实的不一致——现状下 `confirm_plan` 在收集未完成时也会直接建 Run，于是 brief 变成 `submitted`，而 `upsert_active` 只匹配 `collecting/ready`，后续任何回答都会新插一条 brief 行，违反部分唯一索引的意图。

`data/app.db` 目前零业务数据，因此这条 BREAKING 无存量影响。

### 11. 「收集已完成」不阻止提交，提问也不阻止聊天

必答字段在被正确回答前持续追问；可选字段至多问一次。用户答非所问时同一张提问卡片保持不动（派生方案天然如此，不重复追加），对话照常回应；输入框在提问期间始终可用，自由文本句由语言模型按现有优先级规则解释。

### 12. 到达/返程的时段词选中即终局

候选项为：具体时间输入、上午、中午、下午、傍晚、晚上、还不确定。选中时段词即作为最终答案写入字段，按既有保守下界参与规划（`app/planning/helpers.py:ARRIVAL_FLOOR_BY_PERIOD`，傍晚 → 19:00），不再追问，也不影响 readiness。

这同时放宽了 `respect-trip-time-window` 定下的「时段词只追问一次具体时刻」规则，使卡片路径与自由输入路径行为一致——把两条路的规则写成不同的话，正是本仓库已经吃过亏的那类跨层分歧。

备选是选中时段词后再追问一次钟点。被否决：绝大多数用户在规划阶段并不知道精确到达时间，多追问一次只会让六项变成七项。

### 13. 提问卡片与助手气泡分工明确

- 问题只在提问卡片里出现一次，助手气泡不复述它。需要在提示词里明确禁止模型自己把问题再写一遍，否则会回潮。
- 候选项点击走结构化接口，因此**不产生助手气泡**：节奏是「折叠成一行 → 下一张卡片」。卡片文案本身已经给了反馈，再补一句模板回应是重复，且会往对话历史写入非模型文本。

### 14. 澄清提问与字段提问呈现一致

`DialogueClarification` 保留原职责（目标不唯一、确实无法理解等），因为它承担的是字段清单表达不了的歧义。它与字段提问共用同一种卡片；澄清的候选项只随当轮事件下发，因此**刷新后退化为已持久化的文本气泡**，问题本身不丢。

备选是为澄清也给消息表加列。被否决：为了一个低频的一次性事件改表加迁移，收益不抵成本。

### 15. 新提问出现时自动滚动并聚焦；侧边栏不加标记

`.chat-feed` 是 `overflow:auto` 的滚动容器（`style.css:1845`），全仓库没有「新内容自动滚到底」的逻辑，唯一的滚动来自 `focusRun`（`pages.jsx:473`），只在 Run 新进入 `waiting_user` 时触发。提问卡片沿用同一机制：滚动到卡片并聚焦，键盘与读屏用户不会错过。不额外使用 live region 播报，避免与焦点移动造成的播报重复。

侧边栏的 `conversationAttention`（`chat-state.js:86-104`）不为 `collecting` 增加标记：决策 2 之后 collecting 会变得非常普遍，给它加徽标会让注意力模型的信噪比崩掉。

### 16. 结构化回答不广播

响应体直接返回更新后的 brief 与下一个提问，前端就地更新，不发布 SSE 事件。**已知代价**：另一个已打开的标签页要重新加载会话才能同步——这是与语言模型路径不一致的一处局限，明确接受。

备选是用一个 Chat Run 当广播载体。被否决：每点一个选项都会在时间线上留下一个 chat run 实体，被 `activityItems` 渲染成「途途正在思考」再消失，很脏。会话级 SSE topic 的改动面则远超收益。

### 17. 顺手修两个相邻旧缺陷

- `app/core/planning_constraints.py:73-88`：旧的 `attraction_preference` / `food_preference` / `habit_preference` 每次读取都会被重新派生成约束条目，而编辑表从不回写这三个字段，因此用户改一条由它们派生的约束并保存后，同一条偏好会变成两条。本次要往同一块代码写偏好约束，顺手收敛派生逻辑。
- `discardPlanningBrief` 没有二次确认，点一下卡片就静默消失，与 `guided-planning-brief` 的 `放弃需求需要清晰结果` 不符。复用上一次改动新建的 `ConfirmModal`（`frontend/pages.jsx`）补上确认与结果说明。

## Risks / Trade-offs

- **[移除直接开始例外可能让老用户觉得多一步]** → 摘要确认本来就是产品承诺；且 `data/app.db` 零业务数据，无存量习惯需要照顾。
- **[语言模型误判规划意图会凭空开单]** → 提示词收紧意图判定；误开的单可被「清除这份需求」撤销；`collecting` brief 不产生侧边栏标记，因此误开不会造成注意力噪音。
- **[`declined_fields` 需要穿过四处字段白名单]** → 这正是 `docs.md` 问题十四记录的失败模式（新字段只在半数路径生效）。任务中把「四处白名单同步」列为独立可验证项，并为「跳过之后自由输入别的字段」写专门的回归测试。
- **[派生方案丢失真实提问先后]** → 接受；折叠行按固定清单排序，语义不变。
- **[结构化回答路径与对话路径行为不一致]** → 两条路都写同一条 brief 并触发同一套 memory refresh 与校验；自由输入路径额外要求语言模型不要把问题复述一遍。
- **[多标签页不同步]** → 明确接受的局限；提问是单人单端的强交互场景。
- **[提示词仍可能让模型复述问题]** → 为「助手气泡不得复述当前提问」增加契约测试（现有 `tests/test_chat_agent.py` 已有同类提示词断言）。
- **[「收集已完成」与 `ready` 两个近义状态可能被后来者混用]** → 在 CONTEXT.md 中给两者下定义，并写明 `ready ⇏ 收集已完成`。

## Migration Plan

1. 在 `app/core/planning_brief.py` 增加提问清单与「下一个待问字段」的纯函数及单元测试，不接线。
2. 扩展 brief 投影（`declined_fields`、`question`、`collected`、`answered_fields`）并同步四处字段白名单，增加投影测试。
3. 新增结构化回答端点与其字段校验、409 分支测试。
4. 改写前端活动投影为「一条 brief 派生多个条目」，增加 reducer 测试（重放不重复、折叠态、进度）。
5. 实现提问卡片组件、自动定位、清除需求二次确认；调整 `_confirm_plan` 与提示词。
6. 跑通后端与前端全部测试，手工走一遍六项提问到确认的完整流程。

回滚时恢复 `_confirm_plan` 的直接提交分支、前端活动投影与提示词即可；`declined_fields` 是 `data` 里的附加键，留存在数据库中无害，无需回滚数据。
