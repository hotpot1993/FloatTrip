## Context

规划需求单是一条从对话到规划图的唯一通道。对话理解层用 `DialogueDecision.brief_patch` 输出结构化补丁（`app/chat/models.py:69-93`），执行器按 `durable_fields` 白名单过滤后落库（`app/chat/executor.py:132-138`），提交时 `PlanningBriefRepository.submit()` 用 `{**view["data"], ...}` 把需求单数据整体拷进不可变快照（`app/runtime/repositories.py:585-590`），再由 `snapshot_to_state()` 按 `TravelPlanState.model_fields` 白名单透传给规划图（`app/planning/runtime_worker.py:19-28`）。**在字段层面加一个平级字段，就能自动贯穿整条链路**，这是本变更成本可控的原因。

链路的其余环节都不认识"抵达时刻"：

- `required_brief_fields()` 的必填集只有目的地与起止日期（`app/core/planning_brief.py:21-35`）。
- 天数由纯日期差推导：`days = (end - start).days + 1`（`app/chat/executor.py:343-347`），因此抵达日必然被当成一个完整可用日。
- Planner 提示词给的是目的地、天数、每天景点数上限、偏好、结构化约束、逐天「Day N = 日期（星期）」块与天气（`app/planning/nodes.py:211-224,285-299`），没有任何一句约束每天从几点开始。
- `TIME_CHECK_SYSTEM` 只认四类开放时间违规（`app/planning/prompts.py:59-68`）。
- `finalize` 对 `start_time` 原样透传，不排序、不规范、不补齐（`app/planning/nodes.py:812-849`）。

两条必须先尊重的既有约定：

- `guided-planning-brief` 规格声明「目的地及有效日期范围均已收集 → 系统停止必填追问」（`openspec/changes/redesign-conversation-interaction-flow/specs/guided-planning-brief/spec.md:10-12`），并要求可选项不得阻止开始正式规划（同文件 `:25-30`）。因此抵达时刻只能是**软追问**。
- 该规格还限制提问只能落在日期范围、单选、多选或文本四类控件上（同文件 `:14-23`），**没有时间控件**。

## Goals / Non-Goals

**Goals:**

- 让"抵达时刻"成为系统里的一等概念，从收集到核验全链路可追踪。
- 让首日不再从上午开始排一个用户还没到达的行程。
- 让返程日的安排不会排在用户必须赶车之后。
- 在用户信息不足时给出保守但可解释的结果，而不是静默编造。

**Non-Goals:**

- 不定义"每天几点开始"。中间天的起始时刻仍由 Planner 决定。
- 不把抵达时刻变成必填，不改变需求单的 readiness 规则。
- 不把抵达时刻写进长期记忆或用户画像。
- 不新增时间选择控件类型，不引入确定性的行程重排器。
- 不回填存量行程与已有规划快照。
- 不处理多城市分段行程中的中途抵达与离开。

## Decisions

### 1. 抵达与返程时刻是 PlanningBrief 的一等字段

在 `PlanningBriefPatch` 中新增 `arrival_time` 与 `departure_time`，与 `start_date / end_date` 平级，同时加入 `durable_fields` 白名单与 `TravelPlanState`。

备选方案是写成 `trip_constraints` 里一条 `schedule_preference` 自由文本。否决原因：`compatibility_preferences()` 会把节奏、作息、同行、交通、无障碍一并揉进一个 `habit_preference` 字符串（`app/core/planning_constraints.py:217-230`），Planner 提示词只用两行软文本承载它（`app/planning/nodes.py:290-291`），而 `TravelRoute` / `DayRoute` 没有任何字段能落实它——等于把问题从"没有字段"挪到"字段没人读"。

平级字段的收益是链路足够短：提交时 `{**view["data"], ...}` 把需求单数据整体拷进快照（`app/runtime/repositories.py:585-590`），`snapshot_to_state()` 再按 `TravelPlanState.model_fields` 白名单透传（`app/planning/runtime_worker.py:19-28`），首次规划因此不需要额外接线。

**但修改行程不走这条路。** `revision_snapshot_to_state()` 是用父行程的 planner checkpoint **逐字段重建**状态的（`app/planning/runtime_worker.py:48-90`，读取 `travel_start_date` / `days` 等），不是从请求快照继承——`create_run` 对 revision 只继承 `memory_*` / `effective_constraints` / `constraint_coverage` / `trip_budget` 这一组白名单（`app/api/runtime_routes.py:388-396`），日期根本不在其中。因此这两个字段必须**显式**加进 `revision_snapshot_to_state()`，否则「继续修改」会静默丢掉抵达时刻，而首次规划一切正常。

同理，需求单的手动编辑走 `BriefPatch`（`app/api/runtime_routes.py:71-82`）。它不是 `extra="forbid"`，未声明的字段会被 Pydantic **静默忽略**而不是报错，所以字段也必须补到那里。

这条链路上有四处独立的白名单（`durable_fields`、`BriefPatch`、`TravelPlanState`、revision checkpoint），任何一处漏掉都表现为"字段看起来存在但某一条路径上不生效"。测试必须按路径分别覆盖，不能只测首次规划。

### 2. 用户表述与「抵达可用下界」分离

两个概念必须分开，否则会重演"系统以为自己知道用户几点到"的错觉：

- **用户表述**：用户实际说的话，可能是 `18:30`，也可能是「傍晚」。它被保存并在需求单中原样展示。
- **抵达可用下界**：仅当表述不够精确时，系统为排程与核验采用的保守时间下界。它只表达"不得早于何时开始安排"，不代表系统知道了用户的真实抵达时刻。

保守下界表（内部常量，不展示为用户的抵达时刻）：

| 表述 | 抵达下界（时段右端） | 返程取值（时段起点） |
|---|---|---|
| 上午 | 12:00 | 09:00 |
| 中午 | 14:00 | 12:00 |
| 下午 | 17:00 | 14:00 |
| 傍晚 | 19:00 | 17:00 |
| 晚上 | 21:00 | 19:00 |

两列方向**相反**：抵达取时段右端（用户说「傍晚到」通常指那个时段内落地，加上进城与入住，宁可假定他要到时段末尾才能开始活动）；返程取时段起点（返程还要再减去赶车缓冲，按最早可能离开估算才安全）。

用户给出具体钟点时不再套用时段的端点——「下午3点」是 15:00，「傍晚6点」是 18:00。

一个需要留意的边界：「晚上」的右端 21:00 正好等于深夜抵达阈值，因此「晚上到」仍按可排晚间活动处理；只有当用户给出更晚的具体时刻（如 23:00 落地）时，首日才完全不排景点。

数值集中在 `app/planning/helpers.py` 的 `ARRIVAL_FLOOR_BY_PERIOD` 与 `DEPARTURE_EDGE_BY_PERIOD` 两个常量里，调整档位是一行的事。

需求单在展示模糊表述的同时标注「未提供具体时刻」，让用户有机会改成精确时间。

### 3. 抵达时刻不进入长期记忆

抵达时刻是**行程**属性而不是**人**属性。现有记忆抽取已经把任何含日期的内容判为一次性并主动拒绝（`app/chat/memory_service.py:34,50,609-622`），本变更遵循而不是推翻这条设计。理由与代价记录在 `docs/adr/0001-arrival-time-is-trip-scoped.md`。

因此抵达时刻必须随快照冻结（决策 1 已保证），且**每一趟行程都要重新收集**。

### 4. 只在用户主动提到但不精确时软追问

触发条件限定为"用户自己提到了抵达或返程信息，但不够精确"。每趟行程都追问一轮会明显拉长收集过程，而用户从不提及抵达时间时系统也没有依据去假设他在意这件事。

追问必须是软的：按既有规格，抵达时刻属可选信息，问不出也不得阻止需求单进入可提交状态。因此它是**一次澄清机会**，不是一道关卡。

### 5. 追问复用现成的单选澄清机制

`DialogueClarification` 已有 `field`、`question` 与 `options`（最多 8 项字符串）三个字段（`app/chat/models.py:63-67`），前端也已有单选渲染路径。给六个选项——上午 / 中午 / 下午 / 傍晚 / 晚上 / 我填具体时间——选最后一项转文本输入即可。

不新增时间选择控件类型：既有规格的控件注册表只覆盖日期范围、单选、多选与文本（`guided-planning-brief/spec.md:14-23`），扩表需要同时改前后端契约与降级规则，收益不抵成本。

### 6. 首日只排晚餐与一个夜间可玩点

首日的可用时长不足以支撑常规的"每天 N 个景点"配额，硬塞会产出用户到达时景点已经关门、或者必须压缩用餐的路线。因此首日：

- 不排有白天开放时间限制的景点；
- 排一个晚餐与一个夜间可玩点（夜景、步行街一类）；
- 需求单中原样展示用户的抵达表述，让用户理解为什么首日只有一个点。

### 7. 末日必须在返程时刻前预留 2 小时缓冲

2 小时用于覆盖进城到车站/机场的交通、值机或取票与安检。末日景点必须在 `departure_time` 减去 2 小时之前结束，而不是仅仅早于 `departure_time`。缓冲时长作为单一常量定义，便于后续按交通方式细化。

### 8. 边界场景显式退化

- **深夜抵达（晚于 21:00）**：首日不排任何景点，只保留抵达与入住提示。此时连"晚餐 + 夜间可玩点"都不现实。
- **单日行程（`days == 1`）**：首日规则与末日规则会压在同一天上，互相冲突。此时不套用两条规则，改为只排"抵达可用下界到返程可离开时刻"之间的可用窗口；若窗口不足以容纳任何景点，则退化为只给餐饮与提示。

### 9. 核验扩展 TIME_CHECK_SYSTEM，不新增确定性校验器

`time_check ⇄ planner` 的重排回路已经存在（`app/planning/nodes.py:471-563`），新增两类违规即可复用全部现有机制：首日景点 `start_time` 早于抵达可用下界、末日景点 `end_time` 晚于返程可离开时刻。

不新建确定性的 Python 校验器：它会引入一个新的图节点与回边，改动面显著变大，且两层判定可能互相矛盾。抵达时刻本身是用户输入的事实，判断"是否早于下界"是纯比较，交给已有的时间核查 Agent 成本更低。

**覆盖面要在实现前先看清：`time_check` 只存在于首次规划图**（`app/planning/graph.py:85`）。修改流程图（`graph.py:241-250`）与兼容修改图（`graph.py:192-197`）都**没有** `time_check` 节点——这是既有设计，连开放时间也从不核查。因此本决策的两类违规只在首次生成时生效，「继续修改」产出的行程不受核验约束。

把 `time_check` 加进修改流程图等于扩大既有行为（会连带开始核查开放时间），不在本次范围。这一点作为已知限制写进规格与风险，而不是假装核验覆盖全链路。

另外，提示词里的约束措辞必须以 prompt 自己给出的时刻为准，不能自行重复一遍换算。`TIME_CHECK_SYSTEM` 明确要求第 5、6 条违规只在 prompt 给出对应时刻时才成立，避免模型在没有抵达时刻的行程上凭空造出违规。

### 10. 存量数据不回填

已有的行程与规划快照缺少这两个字段。快照透传按字段白名单进行，缺失字段自然取默认空值，因此旧数据无需迁移即可继续读取与修改。不做反推回填：从旧行程的 `plan_json` 反推抵达时间是不可靠的猜测，会把猜测写成事实。

## Risks / Trade-offs

- **[只在用户主动提到时追问，用户不提则首日仍从上午开始]** → 这是有意的范围边界，写进规格与残留说明。若日后要覆盖，需要改成"日期收齐即追问一次"，属于独立提案。
- **[与未归档的 `guided-planning-brief` 规格的协调]** → 该 change 已实现但未归档，其条文尚未进入主规格。我们的追问是**可选**的，与"停止**必填**追问"不构成冲突。一旦该 change 归档，需要在它之外补一条"追问可选信息不得改变 readiness"的说明，避免后续维护者以为两处矛盾。
- **[内部保守下界与用户表述不一致，用户可能以为系统知道他的真实抵达时刻]** → 需求单在展示模糊表述时同时标注"未提供具体时刻"，用户可随时改写为精确时间。
- **[Planner 未必遵守提示词]** → 由决策 9 的核验回环兜底；核验不通过会触发重排。但该回环只在首次规划图里，修改流程没有 `time_check`，因此"继续修改"产出的行程不受核验约束（既有行为，见决策 9）。
- **[四处独立白名单漏一处就半条链路失效]** → `durable_fields`、`BriefPatch`、`TravelPlanState`、revision checkpoint 各有一份字段清单。测试按路径分别覆盖首次规划与修改流程，不合并成一条。
- **[前端与后端对「是否具体时刻」的判断可能不一致]** → 前端要决定标不标"未提供具体时刻"，后端要决定用不用保守下界，两套正则必须给出相同结论（例如「下午3点」两端都必须算具体时刻）。测试用同一批表述交叉验证。
- **[中间天仍无起始时刻定义]** → 明确列为 Non-Goal。首末两天修好之后，"每天几点开始"是另一个问题，需要单独的偏好模型。
- **[新增字段与旧快照的兼容]** → 字段缺失时取默认空值，行为等同现状；测试需覆盖旧快照能正常规划。
- **[抵达时刻有可能与日期范围矛盾（例如抵达时刻所在日期早于 `start_date`）]** → 本次不新增跨字段校验，仅保留既有的"结束日期不早于开始日期"校验；该场景在对话中由追问自然消解。

## Migration Plan

1. 新增字段与白名单，配套 pytest 覆盖字段贯穿（对话补丁 → 需求单 → 快照 → 图状态）与旧快照兼容。
2. 接入追问规则与需求单可编辑控件，配套测试覆盖"提到但不精确时追问"与"未提供时不阻止提交"。
3. 落地首末两天的提示词约束、边界退化与时间核验扩展，配套测试覆盖首日不早于下界、末日缓冲、深夜抵达与单日行程。
4. 手工验证原本的复现场景：用户在对话中说「11月7日傍晚抵达」，确认首日不再出现上午 9:00 的景点。
5. 同步 `docs.md` 与 `CONTEXT.md`。

回滚时移除新增字段与提示词条款即可；已冻结的旧快照不受影响，已生成的行程保持原样。

## Open Questions

- 追问应当由对话理解层直接发出澄清，还是由需求单在检测到模糊表述后发起一次结构化交互？前者更贴近自然对话，后者更容易保证只问一次。
- 抵达可用下界表应当放在提示词模板旁，还是与需求单字段定义放在一起，以便日后按交通方式细化？
- 单日行程的退化规则是否需要额外的产品文案，向用户说明为什么这一天只有一个窗口？
