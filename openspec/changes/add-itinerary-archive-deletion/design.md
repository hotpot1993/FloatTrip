## Context

历史行程页 `HistoryPage`（`frontend/pages.jsx:1903-1989`）从 `GET /api/history` 取数据并平铺成卡片。每张卡片代表 `itineraries` 表的一行，字段只有 `id, parent_id, root_id, version, destination, start_date, end_date, created_at`（`app/core/memory.py:238-244`）。卡片上唯一的操作是整卡点击打开，没有按钮、菜单、长按或右键处理。

「继续修改」不会覆盖原行程，而是派生一行新行程：`root_id` 继承、`version` 加一、`parent_id` 指回派生来源（`app/core/memory.py:140-170`）。因此同一趟旅行在列表里通常占多张卡，各自带「修改版」徽标（`frontend/pages.jsx:1962,1979`）。

删除在数据层会被直接挡住。`runs.result_itinerary_id TEXT REFERENCES itineraries(id)` 未声明 `ON DELETE`（`app/core/database.py:122`），而 `get_conn()` 每次连接都执行 `PRAGMA foreign_keys=ON`（`app/core/database.py:335`），所以只要有任何 Run 记录引用该行程，`DELETE FROM itineraries` 就抛 `IntegrityError`。这是本变更唯一的数据完整性障碍。

仓库里唯一的删除先例是遗忘一条记忆（`app/api/profile_routes.py:115-123` → `app/core/travel_memory.py:343-356`），它是**软删除**，且前端点一下直接生效、没有二次确认（`frontend/pages.jsx:2078`）。项目里另有一个正式的模态框样式（`.modal-backdrop` / `.modal-card`，`frontend/style.css:782,789,803`），但只被规划顾虑弹窗用过一次。

## Goals / Non-Goals

**Goals:**

- 让用户能删掉一条不再需要的行程，且删除语义与用户预期一致。
- 让删除在数据层永远成功，不被后台任务或引用关系阻塞。
- 让删除不可恢复这件事在交互上有足够重量，降低误删。
- 给原本无规格的「行程归档」补上正式契约。

**Non-Goals:**

- 不引入回收站、撤销或软删除。
- 不按"一趟旅行"聚合列表，也不清理版本链的悬空 `parent_id`。
- 不动 `mobile-app` 与 `mobile-prototype`。
- 不做批量删除、多选模式与分页。
- 不改动对话、消息与规划任务的生命周期。

## Decisions

### 1. 删除的作用单位是「一条行程」，不是「一趟旅行」

用户在列表里看到的是卡片，卡片对应一个行程版本；点哪张卡删哪张卡，是唯一没有歧义的映射。若把删除解释成"删掉这趟旅行的全部版本"，用户点掉一张卡却消失了四张，是明确的惊吓。

代价是同一趟旅行的其他版本会保留，并且它们的 `parent_id` 可能指向已删除的行。这个悬空被接受（见决策 4）。列表按旅行聚合是独立的一次改版，不在本次范围。

### 2. 硬删除 + 二次确认，不做软删除

软删除需要在 `load_itinerary`、历史详情、修改流程的父行程校验（`app/api/runtime_routes.py:373-379`）、Run 结果引用等每一处读取路径上补过滤，成本会扩散到整个行程读取面。相比之下，一份行程的误删风险可以用"确认弹窗展示目的地与日期"压到足够低。

因此删除直接移除 `itineraries` 行，规格里明确声明不可恢复。

### 3. Run 的行程引用在删除前置空，而不是级联删 Run

`runs.result_itinerary_id` 是唯一真外键。三个选项里：

- 级联删除引用它的 Run：会丢掉执行历史、`run_events` 与重试链路，与"只删这条行程"的语义不符。
- 改用 `ON DELETE SET NULL`：SQLite 不支持直接修改外键，需要重建 `runs` 表，与仓库现有的轻量 `ALTER TABLE` 迁移风格（`app/core/database.py:236-255`）冲突。
- 删除前置空引用：一条 `UPDATE` 即可，且前端行为天然正确——`RunCard` 的「打开行程 / 继续修改」都判 `run.result_itinerary_id` 是否为真（`frontend/pages.jsx:547`），置空后按钮自动消失。

采用第三种。置空与删除必须在**同一个事务**内完成，否则并发下仍会撞外键。

### 4. 悬空引用一律容忍，不做引用计数

三处引用允许悬空：

- `messages.related_itinerary_id`：它记录的是"这条消息当时针对哪份行程"，属于历史事实。调查确认它写入后前端**从不渲染**——聊天卡片读的是 `run.request_snapshot.related_itinerary_id`（`frontend/pages.jsx:1100`），只有一句说明文案；真正的操作按钮判的是 `run.result_itinerary_id`。保留它比清空更有信息量。
- `itineraries.parent_id`：只被列表用来渲染「修改版」徽标，而"继续修改"取的是**当前打开的这一版**做派生来源（`app/planning/runtime_worker.py:137` 的 `parent_id=state.parent_plan_id`，来源是快照里的 `related_itinerary_id`），不回溯到链首。因此删掉中间某一版不会破坏后续版本的可用性。
- `itineraries.root_id`：没有任何读取路径要求它指向存在的行。

### 5. 常驻删除图标 + 新建通用确认弹窗

卡片右上角放常驻可见的删除按钮，而不是 hover 才出现——触屏没有 hover。卡内按钮必须阻止冒泡，否则会同时触发整卡的 `open(t)`。

确认弹窗新建一个可复用组件，复用既有 `.modal-backdrop / .modal-card / .modal-title` 样式，但**不复用** `ConcernModal`：它的标题写死为"规划师有个顾虑"，语义不符。弹窗展示目的地、日期区间与"不可恢复"警告，确认按钮使用危险样式。删除成功后重新拉取列表，使「共 N 期」计数与卡片同步更新。

### 6. 删除永远不被后台任务阻塞

`runs.result_itinerary_id` 只在 Run **完成时**才写入（`app/planning/runtime_worker.py:122`），所以正在执行的规划或修改任务不会引用到待删行程，删除不会被它挡住。该任务完成后会产出一份新行程，其 `parent_id` 指向已删除的行程——这与决策 4 的悬空容忍是同一件事。

不做"存在活动 Run 引用则拒绝删除"的检查：它会让删除因为用户看不见的后台任务而失败，而项目对"运行中变更"的显式处理要求针对的是**改变运行中的请求**，不是删除一份已经存在的行程。

### 7. 接口沿用 `/api/history` 前缀与既有鉴权语义

删除挂在 `DELETE /api/history/{plan_id}`，与同文件两个 GET 同前缀同文件，避免删除与读取分居两处。鉴权沿用既有三分法（`app/api/history_routes.py:36-42`）：未登录 401、行程不存在 404「行程不存在」、非本人 403「无权访问」。

重复删除返回 404 而不是幂等的 204：与同一个 GET 的失败语义保持一致，前端也能据此区分"删掉了"与"它早就没了"。

### 8. 列表保持一版一张卡

这是决策 1 的另一面，在此明确声明以免被误当成遗漏：本次不引入按 `root_id` 聚合的列表结构。若后续要聚合，需要先定义"一趟旅行"如何展示、如何进入其中某一版，属于独立提案。

## Risks / Trade-offs

- **[硬删除误操作不可挽回]** → 确认弹窗展示目的地与日期，让用户在点击前确认对象；确认按钮使用危险样式，不作默认聚焦项。
- **[置空与删除未在同一事务内导致外键失败]** → 规格要求两者原子完成，并在测试中构造存在 Run 引用的行程验证删除成功。
- **[悬空 `parent_id` 让剩余版本仍显示「修改版」徽标]** → 接受；徽标表达的是"这一版由修改产生"，该事实在删除原版后依然成立。
- **[列表 `LIMIT 50` 导致「共 N 期」与实际总数在超过 50 条时不一致]** → 本次不处理；这是既有行为，与删除功能无关，需要分页提案单独解决。
- **[删除接口与 GET 的鉴权语义不同会造成越权探测]** → 不采用"一律 404"的隐藏策略，而是沿用仓库现有三分法以保持一致；行程 id 是 UUID，探测价值有限。

## Migration Plan

1. 后端新增删除与引用置空操作，配套 pytest 覆盖所有权隔离、引用置空、悬空容忍与重复删除。
2. 前端新增 API 封装与确认弹窗组件，接入 `HistoryPage`。
3. 手工验证：删除无引用的行程、删除被 Run 引用过的行程、删除后列表与计数刷新、删除他人行程被拒。
4. 同步 `README.md` 与 `docs.md` 的功能描述。

回滚只需移除新增的 DELETE 路由与前端入口；数据库无需回滚，已删除的行程不会因为回滚而恢复。

## Open Questions

- 删除成功后是就地移除卡片还是重新拉取整个列表？就地移除更快，但「共 N 期」计数需要同时更新；重新拉取实现更简单且天然一致。
- 删除按钮是否需要同时出现在行程详情页？本次只做列表页；若详情页也要，需要决定删除后跳转到哪里。
